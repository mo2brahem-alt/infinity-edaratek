## Clarifications

### Session 2026-11-07

الإجابات التالية مستخلصة من المصدر وتعليمات المستخدم الأمنية؛ لا تمثل تصويت PM
مفترضًا أو تنفيذًا أو موافقة على المرحلة التالية. لم تُطرح أسئلة تفاعلية، لأن الدليل
حسم نطاق الموافقة دون إنشاء workflow جديد لكل دور. A-04 لم يعد قرار أعمال معلقًا.

- Q: هل تعدد الأدوار مدعوم، وما نطاق الموافقة عند وجود دور حساس؟ → A: نعم، staff+teacher مثبت بتدفق الخدمة واختبارها؛ الموافقة ACCOUNT_LEVEL في users. تُحسب حاجتها من وجود أي school_manager أو supervisor في الأدوار الفعلية، بما فيها legacy، لا من أول role ID. الحساب غير المعتمد الذي يحمل دورًا حساسًا لا يمر عبر دور آخر؛ لا ننشئ موافقة role-level أو نوسع تدفقات إسناد الأدوار.
- Q: ماذا يضمن الرمز السابق وما الذي تعيده الهوية الحالية بعد تغير الدور أو العلاقة؟ → A: يثبت هوية الجلسة فقط؛ يُعاد تقييم النشاط والموافقة والدور والصلاحيات والعلاقة المدرسية في كل طلب. الرمز لا يجمد الامتيازات. الهوية تعيد roles/capabilities وحالة الحساب والموافقة والسياق وحالة تحقق الهاتف بصورة دنيا؛ لا يقرر العميل أهلية الوصول.
- Q: كيف يحسم الوصول المختلط إلى المدارس والملفات والأخطاء دون التباس؟ → A: كل عملية تحتاج دورًا/قدرة وعلاقة صالحة في سياقها نفسه؛ علاقة صحيحة لا تصلح علاقة أخرى. branding العام فقط يبقى عامًا، وكل مرفق خاص بما فيه leave/legacy يحتاج حق العملية الحالي. تسلسل 401/403/409/404/422/429/500 وأولوية الرفض موضحان أدناه؛ لا metadata لسجل أجنبي أو محذوف.
- Q: هل يشمل kill-switch استئناف job قديم يدويًا عبر الطابور؟ → A: نعم؛ false الحالية تمنع بدء كل outbound جديد عند التنفيذ، سواء كان قديمًا أو مؤجلًا أو retry أو مستأنفًا أو dispatch مباشرًا، بصفر real sends في الاختبارات ودون تغيير n8n أو إعادة محاولة uncertain. لا ادعاء بسحب إرسال سبق أن بدأ قبل التعطيل.
- Q: هل حُدد runtime أو عمر token اعتباطي، وما دليل إغلاق H01–H05 وP0؟ → A: لا؛ تُختار وسيلة اختبار غير إنتاجية معتمدة في التخطيط بعد فحص البيئة، وتوثق policy parameters وتختبر حدودها دون اختيار lifetime هنا. H01–H05 ومجموعات P0 الاثنتا عشرة تبقى شروط تحقق منفذة؛ H03/H05 لا يبرران فحص الإنتاج أو تدوير أسرار/تعديل بيئات أثناء هذه المرحلة.

## User Scenarios & Testing *(mandatory)*

الأولوية P1 هنا تعني سيناريو أمني/تشغيلي أساسي؛ لا تساوي تصنيف فجوات اختبارات P0/P1/P2.
كل قصة قابلة للتحقق منفردة ببيانات مصطنعة وخدمات خارجية وهمية، لكن اجتياز قصة واحدة
لا يجيز تجاوز بوابة الجاهزية الجامعة. حالات Given/When/Then هي معايير قبول مطلوبة مستقبلًا.

### User Story 1 - دخول أصلي وهوية حالية موثوقة (Priority: P1)

كمستخدم معتمد ونشط أريد الدخول من عميل أصلي ومعرفة هويتي وصلاحياتي وسياقي المدرسي.

**Why this priority**: الدخول أساس كل الوصول؛ وجود جلسة ويب لا يكفي لعميل أصلي.

**Independent Test**: مستخدم معتمد وجهازان مصطنعان، دون قاعدة إنتاج أو إنشاء Flutter.

**Acceptance Scenarios**:

1. **US01-A — Given** مستخدم ببيانات صحيحة واستيفاء قواعد الموافقة، **When** يدخل ويطلب هويته، **Then** يتلقى جلسة أصلية ذات انتهاء محدد وهوية وقرارات وصول محسوبة بالخادم فقط.
2. **US01-B — Given** جلستان للجهازين نفسيهما بالحساب، **When** يُستخدم كل منهما، **Then** تعملان مستقلتين ولا يلغي الدخول الجديد الجلسة الأخرى أو جلسة المتصفح ضمنيًا.

### User Story 2 - رفض بيانات الدخول دون كشف معلومات حساسة (Priority: P1)

كمستخدم أحتاج ردًا مفهومًا عند فشل الدخول، دون تمكين مهاجم من كشف الحسابات أو الأسرار.

**Why this priority**: المصادقة ومقاومة التخمين بوابة أمنية قبل أي بيانات مدرسية.

**Independent Test**: محاولات كلمة مرور خاطئة وبريد غير موجود وتجاوز حد مضبوط للاختبار.

**Acceptance Scenarios**:

1. **US02-A — Given** بريد غير موجود أو كلمة مرور خاطئة، **When** تجري محاولة الدخول، **Then** تكون النتيجة العامة نفسها 401/INVALID_CREDENTIALS دون تحديد أي جزء صحيح أو إعادة بيانات المستخدم.
2. **US02-B — Given** بلوغ حد المحاولات المعلن، **When** تحدث محاولة أخرى، **Then** يُعاد 429/RATE_LIMITED مع مدة انتظار قابلة للفهم آليًا ولا تصدر جلسة.

### User Story 3 - احترام حالة الموافقة وتغيرها (Priority: P1)

كمدير أو مشرف أريد أن تتوافق صلاحياتي مع اعتماد الحساب الفعلي، لا مع ما يدعيه العميل.

**Why this priority**: الوصول قبل الاعتماد أو بعد الإيقاف قد يعرّض المدارس للخطر.

**Independent Test**: حالات pending_approval وapproved وrejected وis_active في النموذج الحالي.

**Acceptance Scenarios**:

1. **US03-A — Given** بيانات صحيحة لحساب school_manager أو supervisor يلزمه اعتماد وغير مستوفٍ له، **When** يحاول الدخول، **Then** لا تصدر جلسة تشغيلية وتُعاد حالة رفض ثابتة دون اختراع approval statuses جديدة.
2. **US03-B — Given** رمز سابق وحساب يجمع staff مع school_manager أو supervisor، **When** يُعطّل الحساب أو تصبح موافقته pending_approval/rejected، **Then** يمنع الطلب التشغيلي التالي لكل أدواره ولا يعيد current-user بيانات تشغيلية؛ الاعتماد اللاحق لا يحيي رمزًا ألغي أو انتهى، ولا يعطي علاقة مدرسة غير مأذونة.

### User Story 4 - الوصول إلى سياق مدرسي مأذون (Priority: P1)

كمستخدم أريد بيانات المدرسة المسموح بها فعلًا دون اختيار هوية tenant من العميل.

**Why this priority**: حدود المدارس شرط إطلاق لا تفضيل واجهة.

**Independent Test**: مدرستان ومدير وموظف ومشرف وعلاقات مختلفة مصطنعة.

**Acceptance Scenarios**:

1. **US04-A — Given** ارتباط صالح بمدرسة نشطة، **When** يطلب المستخدم موردًا ضمن صلاحياته، **Then** يُحسم school context من علاقاته الموثوقة وتظهر البيانات المسموح بها فقط.
2. **US04-B — Given** مشرف مسموح له باختيار أكثر من مدرسة، **When** يحدد مدرسة ضمن العملية المصرح بها، **Then** يتحقق الخادم من العلاقة لكل طلب؛ اختيار مدرسة غير مرتبطة لا يمنحه سياقها.

### User Story 5 - منع الوصول العابر للمدارس (Priority: P1)

كمدرسة أحتاج ألا تكشف المعرفات أو الفلاتر أو الروابط بياناتي لمستخدم مدرسة أخرى.

**Why this priority**: هذا هو invariant العزل متعدد المدارس.

**Independent Test**: مصفوفة وصول سلبية بين المدرستين لكل endpoint يجهز في هذه الميزة.

**Acceptance Scenarios**:

1. **US05-A — Given** مستخدم المدرسة أ ومعرف مورد المدرسة ب، **When** يطلبه أو يعدّله أو ينزله، **Then** يُرفض الوصول دون bytes أو metadata حساسة أو تغيير في ب.
2. **US05-B — Given** محاولات school_id أو relationship IDs أو فلاتر أو pagination عابرة للمدارس، **When** يرسلها العميل، **Then** لا تغيّر السياق أو totals أو النتيجة إلى بيانات المدرسة الأخرى.

### User Story 6 - مهام الموظف ضمن التفويض والمدرسة الحالية (Priority: P1)

كموظف أريد قائمة مهامي وتفاصيلها المأذونة فقط، بما في ذلك بعد النقل بين المدارس.

**Why this priority**: يعالج H02 حيث تختلف حدود list عن سياسة show.

**Independent Test**: مهام لعدة موظفين ومدرستين ونقل موظف مع بقاء المهام التاريخية.

**Acceptance Scenarios**:

1. **US06-A — Given** موظف نشط وله مهام مسندة في مدرسته الحالية، **When** يسردها أو يفتحها، **Then** تظهر مهامه المسموحة فقط، ولا تكشف القائمة رسائل/مرفقات غير مطلوبة أو مهام زميل غير مأذونة.
2. **US06-B — Given** موظف انتقل من أ إلى ب وما زالت مهام أ تحمل assigned_to الخاص به، **When** يستخدم list/show/filters/pages/direct URLs، **Then** لا تظهر مهام أ أو تفاصيلها أو counts الخاصة بها.

### User Story 7 - تنزيل مرفق خاص مأذون (Priority: P1)

كمستخدم مخول أريد تنزيل ملف تابع لسجل مأذون دون جعله أصلًا عامًا.

**Why this priority**: يربط حق الملف بحق المدرسة والسجل والعملية.

**Independent Test**: ملف مصطنع خاص وحق عملية صالح، مع فحص المحتوى والـmetadata المعادة.

**Acceptance Scenarios**:

1. **US07-A — Given** جلسة صالحة وحق المدرسة والسجل والتنزيل، **When** يطلب المستخدم الملف، **Then** يتلقى الملف الصحيح واسمًا ونوعًا مناسبين دون كشف مسار التخزين الداخلي.
2. **US07-B — Given** رابط تنزيل خاص معروف، **When** يفقد صاحبه صلاحية الوصول قبل طلب جديد، **Then** لا يعيد استخدام الرابط حقه السابق حتى إن بقي الرابط ذاته صالح الشكل.

### User Story 8 - رفض تنزيل غير مأذون بما فيه مرفقات الإجازات (Priority: P1)

كصاحب بيانات أحتاج حماية المرفقات حتى ممن يعرف الرابط أو يملك صلاحية تقويم فقط.

**Why this priority**: يعالج H01 وM01 وM07، ولا يكفي فحص المدرسة وحده.

**Independent Test**: زائر، مستخدم مدرسة أخرى، وصاحب صلاحية calendar دون leave download.

**Acceptance Scenarios**:

1. **US08-A — Given** زائر أو مستخدم مدرسة أخرى ورابط ملف خاص/قديم، **When** يطلبه مباشرة أو عبر مسار عام بديل، **Then** لا يحصل على الملف أو metadata كاشفة.
2. **US08-B — Given** مستخدم من المدرسة نفسها يملك حق التقويم وحده، **When** يطلب مرفق إجازة، **Then** يُرفض؛ يُسمح فقط لصاحب حق الإجازات/المرفق المحدد وفق التفويض الحالي المعتمد.

### User Story 9 - إبقاء الأصول العامة المقصودة متاحة (Priority: P2)

كزائر أريد الشعارات وصور العلامة العامة دون فرض تسجيل دخول على أصل عام مقصود.

**Why this priority**: منع تسريب الملفات لا يستلزم تعطيل العلامة العامة أو ترحيل كل الصور.

**Independent Test**: شعار مصطنع معلن عام، ومرفق مؤسسي خاص على مسار عام قديم.

**Acceptance Scenarios**:

1. **US09-A — Given** شعار مصنف صراحة PUBLIC ASSET، **When** يطلبه الزائر، **Then** يبقى قابلًا للقراءة بالطريقة العامة الموثقة.
2. **US09-B — Given** مرفق خاص لمهمة/طالب/إجازة، **When** يوجد تاريخيًا على public disk أو يدعي الطلب أنه public، **Then** لا يتحول تصنيفه إلى أصل عام ولا يتجاوز التفويض.

### User Story 10 - تعطيل WhatsApp يمنع حتى المهام القديمة (Priority: P1) - SUPERSEDED_BY_PM2026-11-09 (historical only)

كمسؤول أريد أن يكون تعطيل outbound ضمانًا فعليًا عند التنفيذ لا مجرد منع enqueue جديد.

**Why this priority**: H04 يهدد شرط الصفر إرسال رغم flag=false.

**Independent Test**: jobs قديمة ومؤجلة ومعاد تجربتها وdispatch مباشر، مع outbound fake فقط.

**Acceptance Scenarios**:

1. **US10-A — Given** job أُنشئ حين كان الإرسال مفعّلًا ثم أصبحت القيمة الحالية false قبل الإرسال، **When** يُنفّذ، **Then** تكون محاولات outbound الفعلية صفرًا ولا يُسجل أنه أرسل أو سُلّم.
2. **US10-B — Given** التعطيل مستمر، **When** تحدث retry أو delayed/new job أو استئناف يدوي عبر معالجة الطابور العادية أو محاولة dispatch مباشرة، **Then** تبقى محاولات الإرسال صفرًا مع حفظ منع التكرار وحالة التسليم غير المؤكد دون إنشاء إرسال بديل.

### User Story 11 - عقد أخطاء وبيانات ثابت (Priority: P1)

كعميل أصلي أحتاج فهم النتيجة آليًا دون تحليل جملة عربية أو إنجليزية.

**Why this priority**: يزيل اختلاف envelopes والـredirects الذي يمنع استهلاكًا موثوقًا.

**Independent Test**: أمثلة resource/collection وكل فئات الخطأ مع قيم فارغة وحدود pagination.

**Acceptance Scenarios**:

1. **US11-A — Given** مدخلات غير صالحة أو نقص تفويض، **When** يطلب العميل عملية، **Then** يتلقى 422 مع field errors أو 403 مع code ثابت، لا redirect/HTML، ولا سرًا ضمن الخطأ.
2. **US11-B — Given** قائمة كبيرة/فارغة أو تعارض أو rate limit أو خطأ خادم، **When** تُطلب، **Then** تطابق البنية والرموز والحدود الموثقة في FR-017 وFR-030–032 دون تغير النوع بحسب وجود per_page.

### User Story 12 - استمرار مسارات Vue/Inertia (Priority: P1)

كمستخدم ويب أريد استمرار دخولي ووظائف مدرستي أثناء إضافة عميل جديد للخادم نفسه.

**Why this priority**: الموبايل إضافة، وليس تحويل الويب إلى REST أو تبديل backend.

**Independent Test**: اختبارات regression لمسارات المتصفح والتدفقات والخدمات المتأثرة.

**Acceptance Scenarios**:

1. **US12-A — Given** جلسة متصفح صالحة، **When** يدخل عميل أصلي أو يخرج، **Then** لا تتغير جلسة المتصفح أو CSRF أو Inertia redirects بلا تغيير أمني مقصود موثق ومعتمد.
2. **US12-B — Given** التدفقات الحالية للموافقة والاشتراكات والإشراف والمهام، **When** تُجهز واجهات الموبايل، **Then** تبقى نتائج الخدمة نفسها وصلاحياتها المأذونة مع اجتياز regression؛ إصلاح تجاوز أمني ليس سلوكًا يجب الحفاظ عليه.

### User Story 13 - إلغاء الجلسة أو الجهاز المفقود (Priority: P1)

كصاحب حساب أريد إلغاء وصول جهازي أو جلساتي دون تمكين شخص آخر من التحكم بها.

**Why this priority**: فقد الجهاز أو نسخ رمز يجب ألا يترك وصولًا غير قابل للإيقاف.

**Independent Test**: جلستان للحساب وحساب آخر ومحاولات reuse بعد الإلغاء.

**Acceptance Scenarios**:

1. **US13-A — Given** جلستان مستقلتان، **When** يُلغى رمز إحداهما أو تُسجل الخروج، **Then** يرفض طلبها التالي 401 وتبقى الأخرى صالحة إن لم تتغير صلاحية الحساب.
2. **US13-B — Given** صاحب حساب بجلسة صالحة، **When** يلغي جهازًا محددًا أو جميع جلساته الأصلية، **Then** يُرفض reuse لكل ما أُلغي، ولا يستطيع حساب آخر سرد أو إلغاء جلساته بمعرفات مخمنة.

### User Story 14 - اختبارات قابلة للتشغيل وبوابة مراجعة موثقة (Priority: P1)

كمراجع PM أريد دليلًا منفذًا على الجاهزية، لا اعتبار وجود ملفات الاختبار نتيجة نجاح.

**Why this priority**: Phase 0 اكتشف الاختبارات ولم يتمكن من تشغيلها.

**Independent Test**: إعادة تنفيذ طريقة الاختبار المعتمدة في بيئة غير إنتاجية ببيانات وهمية.

**Acceptance Scenarios**:

1. **US14-A — Given** runtime غير إنتاجي موثق ومعزول، **When** تُشغّل مصفوفة P0 والاختبارات المطلوبة وregression، **Then** يمكن إعادة تشغيلها وتُحفظ النتائج الفعلية وأوامرها دون أسرار أو إرسال خارجي.
2. **US14-B — Given** runtime مفقود أو P0 فاشل/متخطى أو High blocker أو قرار أعمال معلق، **When** تُراجع الجاهزية، **Then** تبقى MOBILE_BACKEND_NOT_READY ولا يُبدأ Flutter بسبب وجود endpoints فقط.

### Edge Cases

- **EC-01**: رمز انتهى تمامًا عند expires_at؛ الطلب عند الحد أو بعده مرفوض 401.
- **EC-02**: رمز ألغي ثم أُعيد استخدامه؛ لا يعيده login لاحق أو retry إلى الصلاحية.
- **EC-03**: حذف المستخدم بعد إصدار الرمز؛ لا هوية أو بيانات في الطلب اللاحق.
- **EC-04**: تعطيل/رفض الحساب أثناء وجود رمز؛ تتغير نتيجة الوصول في الطلب التالي.
- **EC-05**: حساب يجمع legacy/Spatie roles؛ تطبق A-04 المحسومة على أي دور حساس بغض النظر عن ترتيب role IDs، ويمنع pending/rejected الوصول التشغيلي للحساب كله عند وجوده.
- **EC-06**: نقل موظف بين المدارس أو تغيير تفويضه؛ يعاد حسم السياق وتختفي بيانات المدرسة السابقة.
- **EC-07**: تعليق المدرسة بعد الدخول؛ لا تتاح العمليات المدرسية أو quick-setup المحمية.
- **EC-08**: مستخدم بلا مدرسة؛ تعاد حالة سياق غير مكتمل، ولا تُختار مدرسة من مدخلاته ضمنيًا.
- **EC-09**: IDs أجنبية في parent/child أو search/filter/sort/page؛ لا بيانات أو counts عابرة للمدارس.
- **EC-10**: معرف مسار مشوه أو جسم طلب غير صحيح؛ رد ثابت وفق FR-031 دون stack trace.
- **EC-11**: ملف/سجل مفقود أو محذوف أو رابط خاص منتهي؛ لا محتوى خاص، ورد 404 مناسب.
- **EC-12**: سُحب تفويض الملف قبل طلب التنزيل الجديد؛ الرابط المعروف لا يمنحه وصولًا.
- **EC-13**: ملف خاص قديم في public أو cache/preview بديل؛ لا تعيد البدائل فتحه.
- **EC-14**: تصنيف asset عام مقصود مقابل مرفق خاص؛ لا ترحيل عام غير مبرر ولا ثقة بتصنيف العميل.
- **EC-15**: job قديم/مؤجل أُنشئ قبل التعطيل؛ يفحص قرار الإرسال الحالي عند التنفيذ.
- **EC-16**: retry/direct dispatch أو استئناف يدوي عبر الطابور أثناء التعطيل؛ صفر outbound ولا ادعاء sent/delivered، ولا يحتفظ worker/job قديم بإذن إرسال سابق.
- **EC-17**: duplicate request أو callback/claim مكرر؛ لا إرسال مزدوج ولا تجاوز تفويض، وreplay مرفوض.
- **EC-18**: page خارج آخر صفحة صحيحة؛ collection فارغة بنفس envelope؛ page<1 أو per_page>100 تُرفض 422.
- **EC-19**: بلوغ rate limit أو OTP cooldown؛ 429 بالحد الشبكي أو 422 بقاعدة تحقق موثقة، مع code ووقت انتظار ثابتين وفق FR-031 وSR-021.
- **EC-20**: إرسال OTP متزامن أو تغيير الهاتف؛ لا تجاوز budget/cooldown ولا تحقق لرقم غير الرقم المرجعي الحالي.
- **EC-21**: error أو JSON يحتوي حقولًا غير مسموحة/أسرار/مسار تخزين؛ لا تسرب عبر نجاح أو فشل أو logs.
- **EC-22**: إرسال بدأ بالفعل قبل سريان التعطيل؛ لا يمكن افتراض سحبه من المزود، لكن لا تبدأ محاولة إرسال جديدة بعد التعطيل ولا يُعاد إرسال uncertain تلقائيًا.

- **SR-018**: MUST تعمل security/regression tests ببيانات مصطنعة وDB وcache وqueue وmail معزولة عن الإنتاج، مع منع real-provider network أثناء الاختبارات. (IX, X)
- **SR-019**: MUST تُحفظ الأعمال السابقة والموافقات المستقلة؛ لا commit/push/merge/deploy/destructive DB/production integration activation بلا إذن منفصل، ولا تعديل staging/production خلال specification. (X, XI, XII)
- **SR-020**: MUST تسمح error/request identifiers بتتبع العطل دون كشف وجود مورد أجنبي أو traces أو أسرار؛ النص المترجم لا يغير machine code أو الصلاحية. (L03; V, XIII)
- **SR-021**: MUST لا تسمح عمليات OTP الحالية المتأثرة بتجاوز budget/cooldown عبر تغيير IP أو طلبين متزامنين؛ يُتحقق الرقم المرجعي الحالي بالخادم ويُبطل التحقق القديم عند تغييره، مع حفظ الرسائل disabled وفحص الرفض آليًا. (L04; I, VIII, IX)

- **SR-024**: MUST لا يملك مستخدم سرد/إلغاء جلسات مستخدم آخر أو إحياء رمز جهاز مفقود/ملغى؛ الإلغاء لا يعتمد على ثقة بمعرف جلسة من العميل. (VI)

### Observable Error Contract

أسماء codes التالية عقد أول مقترح قابل للاختبار، وليست ادعاء بأنها موجودة حاليًا.

| النتيجة | HTTP/code | المخرجات المطلوبة |
|---|---|---|
| نجاح مورد/قائمة/إنشاء | 200 أو201 للعملية الموثقة | data ثابتة؛ meta/links للقائمة؛ nullability موثقة |
| logout/revoke ناجح | 204 | لا محتوى؛ طلب محمي بالرمز الملغى بعده401 |
| invalid credentials | 401 / INVALID_CREDENTIALS | نفس النتيجة العامة لبريد مجهول أو كلمة مرور خاطئة |
| مصادقة غائبة/رمز غير صالح | 401 / UNAUTHENTICATED | لا بيانات محمية ولا redirect أو fallback |
| حساب غير مسموح بعد تحقق بياناته/جلسة سابقة | 403 / ACCOUNT_PENDING_APPROVAL أو ACCOUNT_REJECTED أو ACCOUNT_DISABLED | عند is_active=false للأسباب المعتادة لانتظار/رفض الحساب يُقدّم code الموافق لـpending/rejected إن كان يخضع للموافقة؛ غير ذلك ACCOUNT_DISABLED؛ لا حالات موافقة جديدة |
| نقص تفويض عملية | 403 / FORBIDDEN | لا بيانات العملية؛ لا كشف مورد بمدرسة أخرى |
| مدرسة موقوفة | 403 / SCHOOL_SUSPENDED | لا عمليات/quick-setup مدرسية محمية |
| سياق غير مكتمل | 409 / SCHOOL_CONTEXT_REQUIRED | يميز إعداد المدرسة عن خطأ كلمة المرور؛ لا يختار school_id من العميل |
| غير موجود/محذوف/غير مرئي/رابط خاص منتهٍ | 404 / NOT_FOUND | لا metadata تثبت وجود مورد أجنبي |
| business conflict/impact confirmation | 409 / BUSINESS_CONFLICT أو IMPACT_CONFIRMATION_REQUIRED | تفاصيل غير حساسة للتعارض/التأكيد مع بقاء القرار بالخادم |
| payload/query غير صالح | 422 / VALIDATION_FAILED | errors بأسماء الحقول؛ malformed path ID يمكن404 دون trace |
| rate limit | 429 / RATE_LIMITED | Retry-After ومدة انتظار موثقة؛ لا رمز أو بيانات العملية |
| خطأ غير متوقع | 500 / INTERNAL_ERROR | message عامة وrequest_id غير حساس؛ لا stack/secret/provider internals |

أولوية الرفض للطلب الأصلي التشغيلي: غياب/فساد/انتهاء/إلغاء الرمز أو حذف صاحبه401؛
ثم أهلية الحساب403 وفق A-04؛ ثم حق endpoint العام403 دون كشف وجود record؛ ثم
سياق المدرسة المطلوب409 إن لم يكتمل أو403 عند تعليقها؛ ثم record visibility404
للمفقود/المحذوف/المدرسة الأجنبية؛ ثم حق العملية على السجل المرئي403. محدودية المعدل
قد توقف الطلب بـ429 قبل تنفيذه مع الحفاظ على عدم كشف الحساب/السجل. login يقيم
credentials أولًا ولا يكشف pending/rejected إلا بعد تحققها. payload/query المشوه422
في العملية المأذونة، وmalformed path404؛ لا يعتمد الاختبار على نص message. استثناء
logout المنهي للرمز الحالي فقط منصوص عليه في FR-006 ولا يمنح وصول أعمال.

حالة OTP cooldown/attempt rule الحالية التي تعامل كتحقق يمكن أن تبقى422 مع code مثل
OTP_COOLDOWN وretry_after_seconds؛ تجاوز limiter الشبكي429. تُختبر الدلالتان دون اعتماد
العميل على نص الخطأ. لا يُعاد تعريف الأخطاء القديمة للويب بلا ضرورة توافق موثقة.

### Key Entities *(include if feature involves data)*

- **User / Account State**: المستخدم الحالي ونشاطه وموافقته وأدواره وقرارات وصوله؛ لا نسخة حساب جديدة للعميل الأصلي.
- **Native Device Session**: صاحب الجلسة ووصف الجهاز ووقت إصدار/انتهاء/إلغاء مرئي آليًا دون كشف سر الرمز في قوائم الجلسات.

- **Outbound Decision / Dispatch State**: قرار enabled الحالي وهوية claim/idempotency وحالة delivery/uncertain دون كشف تفاصيل التكامل للعميل.
- **Contract / Verification Evidence**: نسخة العقد والحالات والأخطاء وحدود الصفحات وأدلة الاختبارات ومراجعة blockers اللازمة للجاهزية.
